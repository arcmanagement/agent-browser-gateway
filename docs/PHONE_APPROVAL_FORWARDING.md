# Phone Approval Forwarding Design Note

Phone approval forwarding lets a user review a desktop ABG approval request from a phone while the
actual browser operation still runs on the user's desktop Gateway and extension. The phone is a
secondary approval surface, not a remote browser-control endpoint.

## User Goal

The user can step away from the desktop, receive a short approval request on a phone, and approve or
deny the pending desktop operation after confirming what the agent is asking ABG to do.

The flow must preserve ABG's existing consent model:

- The target tab is already shared by the desktop extension.
- The desktop Gateway remains the only component that can execute the operation.
- Approval forwarding never grants a phone direct tab access, screenshot access, clipboard access,
  plugin execution, or arbitrary command submission.

## Approval Request UI

The phone UI should show one pending approval at a time with enough information to decide without
opening a full desktop session.

Required fields:

| Field | Purpose |
| --- | --- |
| Operation summary | Human-readable intent, such as "Click the Submit button" or "Navigate this tab to example.com". |
| Target origin | The origin from the desktop tab, such as `https://example.com`. Show the registered domain and full origin when space allows. |
| Requested action | The normalized ABG method and action family, such as `click`, `fill`, `upload`, `navigate`, `dialog_accept`, or `eval_script`. |
| Requester identity | The local requester that initiated the command, including CLI process identity when available, plugin name when applicable, and desktop device profile label. |
| Expiry | Absolute expiry time and a countdown. Expired approvals are rendered as disabled and cannot be submitted. |

Recommended supporting fields:

- Desktop session label, Gateway instance ID, and paired device name.
- Target tab title and tab reference when available.
- Sensitive-value summary instead of raw secrets. For example, show "fills 18 characters" rather
  than the full field value unless the local command explicitly marks a value as safe to display.
- Risk badge for high-impact actions such as navigation, upload, dialog handling, JavaScript eval, or
  sandbox browser-owned controls.
- Audit statement explaining that the decision will be recorded in the desktop audit log.

The decision controls should be asymmetric:

- Primary visible action: `Deny`.
- Secondary protected action: `Approve`, requiring a press-and-hold or slide gesture.
- Destructive or broad actions, including `eval_script`, require a short challenge that matches the
  desktop session code.

## Approval Payload

The forwarded payload should be generated by the desktop Gateway after the extension has created the
normal approval request. It should contain only data needed for the phone UI and the decision binding.

Minimum payload:

```json
{
  "approvalId": "apr_01J...",
  "requestNonce": "base64url-random",
  "createdAt": "2026-07-09T10:15:30Z",
  "expiresAt": "2026-07-09T10:16:30Z",
  "desktop": {
    "gatewayInstanceId": "gw_01J...",
    "profileLabel": "Work laptop",
    "sessionCode": "482-913"
  },
  "requester": {
    "kind": "cli",
    "processLabel": "abg",
    "pluginName": null
  },
  "target": {
    "tabId": 42,
    "tabRef": "t1",
    "title": "Example Admin",
    "origin": "https://example.com",
    "urlHost": "example.com",
    "accessMode": "manual"
  },
  "action": {
    "method": "click",
    "family": "write",
    "summary": "Click the Submit button",
    "selectorSummary": "button[type=submit]",
    "sensitiveValuePolicy": "omitted"
  },
  "risk": {
    "level": "medium",
    "reasons": ["write_operation"]
  }
}
```

Decision response:

```json
{
  "approvalId": "apr_01J...",
  "requestNonce": "base64url-random",
  "decision": "allow",
  "decidedAt": "2026-07-09T10:15:48Z",
  "approverDeviceId": "phone_01J...",
  "desktopSessionCode": "482-913"
}
```

The desktop Gateway must validate the response against the current pending approval before sending
the decision to the extension.

## Misuse Protections

### Impersonation

- Pair phones with a user-controlled private channel, such as the same Tailnet or LAN pairing flow.
  ABG must not operate a cloud approval relay.
- Bind each paired phone to a desktop Gateway instance ID and a rotating session key.
- Sign or MAC every forwarded approval payload and decision response with the pairing session key.
- Display the desktop profile label and short session code on both the desktop and phone during
  pairing and high-risk approvals.
- Include requester identity in the UI and audit log. Plugin-originated requests must show the plugin
  name and command label.

### Stale Approvals

- Keep expiry short. The MVP should default to the existing local approval timeout, capped at 60
  seconds for forwarded approvals.
- Reject decisions after `expiresAt`, after tab navigation, after tab close, after tab revoke, after
  Gateway restart, or after the original extension approval request disappears.
- Use one-time nonces and remove the pending approval after the first allow or deny decision.
- Render expired requests as read-only history, not actionable prompts.

### Accidental Approval

- Make denial easier than approval.
- Require press-and-hold or slide-to-approve for all phone approvals.
- Require a desktop session-code challenge for JavaScript eval, uploads, navigation to a different
  origin, dialog accept/prompt submission, and sandbox browser-owned controls.
- Never approve more than one operation with a single phone gesture.
- Show value summaries for fills and uploads, but omit raw sensitive values by default.

### Mismatched Desktop Sessions

- Bind the payload to `gatewayInstanceId`, desktop profile label, tab ID, tab ref, target origin,
  access mode, approval ID, and request nonce.
- Before executing, the desktop Gateway re-checks that the pending approval still points at the same
  extension approval request and the same target origin.
- A phone can be paired with multiple desktops, but each approval screen must show exactly which
  desktop session will execute the command.
- Decisions for another Gateway instance, another extension profile, another tab, or another origin
  are rejected and audited as mismatches.

## MVP Scope Decision

MVP should be a private-network forwarding path for existing operation approvals only.

Included:

- Desktop Gateway exposes pending approval summaries to paired phones over the same user-controlled
  remote pairing channel planned for Phase 4.
- Phone can allow or deny one pending desktop approval at a time.
- Existing desktop extension approval logic remains the source of truth for timeout and final
  execution.
- Decisions are written to the desktop audit log with approver device ID, approval mode, outcome,
  target origin, action family, and mismatch or timeout reason when applicable.

Excluded from MVP:

- ABG-operated cloud relay, push notification service, account system, or telemetry.
- Phone-originated browser commands.
- Phone screenshots, DOM reads, clipboard inspection, file upload selection, plugin execution, or
  arbitrary command entry.
- Bulk approvals or durable "always allow from phone" policies.
- Approval forwarding for unshared tabs or for desktops that are not explicitly paired.

The first implementation should prefer denial on any ambiguity. If the phone, desktop Gateway, or
extension cannot prove that the approval response matches the live pending request, the operation is
denied and the audit log records the reason.
