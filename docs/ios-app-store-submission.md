# iOS App Store Submission

ABG Companion ships as a second platform on the same App Store Connect record as the Mac app.
The macOS path is documented separately in [app-store-submission.md](app-store-submission.md);
the two share an app record and a bundle identifier but nothing else about how a build is made.

## Record

```text
Apple ID: 6789562058
Platform: iOS (second platform on the existing record)
Bundle ID: jp.co.arcm.AgentBrowserGateway
Safari extension: jp.co.arcm.AgentBrowserGateway.<extension target>
Team: M46W5MVAQP
Release: Manual release after App Review approval
```

The iOS target family is `1,2`. **The app ships for iPhone and iPad**, so App Review may evaluate it
on either. See [Device family](#device-family) before writing any user-facing copy.

## Differences from the macOS path

| | macOS | iOS |
| --- | --- | --- |
| Project | SPM package, no `.xcodeproj` | `ios/ABGCompanion`, Xcode project generated by `xcodegen` from `project.yml` |
| Signing | explicit identities and a `.provisionprofile` passed to `scripts/dist-mac-app-store.sh` | `CODE_SIGN_STYLE: Automatic` with `DEVELOPMENT_TEAM`, resolved by `-allowProvisioningUpdates` |
| Artifact | signed `.pkg` | `.ipa` exported from an `.xcarchive` |
| Version source | `VERSION` / `BUILD_NUMBER` environment variables | `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` in `ios/ABGCompanion/project.yml` |

The version lives in the checked-in `project.yml`, not in the generated project. Edit it there and
regenerate, or `xcodegen` will overwrite the change.

## Build and upload

Run this on the maintainer Mac. Nothing here belongs in CI: the App Store Connect credential is a
local keychain item and the signing identity is a local private key.

1. Raise the build number and regenerate the project.

   ```bash
   # edit CURRENT_PROJECT_VERSION in ios/ABGCompanion/project.yml
   cd ios/ABGCompanion && xcodegen generate
   ```

2. Archive.

   ```bash
   xcodebuild -scheme ABGCompanion -destination 'generic/platform=iOS' \
     -configuration Release -archivePath /path/to/build.xcarchive \
     -allowProvisioningUpdates archive
   ```

3. Export. Use `manageAppVersionAndBuildNumber: false` so the export does not silently renumber the
   build you just set.

   ```xml
   <key>method</key><string>app-store-connect</string>
   <key>teamID</key><string>M46W5MVAQP</string>
   <key>signingStyle</key><string>automatic</string>
   <key>uploadSymbols</key><true/>
   <key>manageAppVersionAndBuildNumber</key><false/>
   ```

   ```bash
   xcodebuild -exportArchive -archivePath /path/to/build.xcarchive \
     -exportOptionsPlist ExportOptions.plist -exportPath /path/to/export \
     -allowProvisioningUpdates
   ```

4. Validate, then upload. `ABG_APP_STORE_CONNECT` is a local keychain item holding an
   app-specific password; the value never needs to be read or copied.

   ```bash
   xcrun altool --validate-app -f "/path/to/export/Agent Browser Gateway.ipa" -t ios \
     -u <apple-id> -p "@keychain:ABG_APP_STORE_CONNECT"
   xcrun altool --upload-app -f "/path/to/export/Agent Browser Gateway.ipa" -t ios \
     -u <apple-id> -p "@keychain:ABG_APP_STORE_CONNECT"
   ```

   A successful upload prints a Delivery UUID. That UUID is the row id of the build in the App Store
   Connect build picker, which is the only reliable way to confirm you are selecting the build you
   just uploaded rather than one with the same number from an earlier attempt.

5. Move the `.xcarchive` somewhere durable. It holds the dSYMs for a shipping build, so it does not
   belong in `/tmp`:

   ```bash
   mv /path/to/build.xcarchive \
     ~/Library/Developer/Xcode/Archives/<date>/"Agent Browser Gateway <date> iOS <version> (<build>).xcarchive"
   ```

6. Wait for processing. The build appears under TestFlight before it can be attached to a version;
   until then the version page's build picker does not list it.

## Device family

The app ships for iPhone and iPad, so a review can run on either, and an iPad is not the less likely
of the two. Do not assume the reviewer holds an iPhone.

Keep every string a person reads on the device free of a specific device name. Write "this device",
not "your iPhone". This applies to the companion app and to the Safari extension popup, which is
what a reviewer opens when checking why the extension requests website access.

Names that identify the *platform* rather than the user's hardware are fine and are referenced by
docs, the installed skill, and CLI output — the `profileLabel` reported to the Gateway and the
`unsupported_on_safari` reasons stay as they are.

Verify on an iPad simulator before submitting, not only on an iPhone. `XCUIDevice.shared.orientation`
from a UI test is the practical way to check landscape, since the Simulator's rotate menu items are
disabled unless the app is frontmost.

## Review notes

The review notes field is shared with the macOS submission in spirit but not in content. Notes
written for the Mac app describe launching from `/Applications`, a menu bar icon, and a Terminal
command — a reviewer on an iPad can do none of that, and a submission whose notes cannot be followed
invites a completeness rejection.

iOS notes must lead with the steps that need **no paired Mac**, and must state that the unpaired
pairing screen is the expected state rather than a defect. Cover, in this order: what the app is and
who it is for; what a reviewer sees without a Mac; numbered steps that work standalone, including
enabling the extension under Settings > Apps > Safari > Extensions; the full flow for a reviewer who
does have a Mac; why the extension requests read and write access; the permissions the app requests
and why; and the absence of an account, purchases, or any external service.

The field caps at 4000 characters.

## Handling a rejection

Read the message on the submission detail page. Guideline 2.1 arrives in two shapes and they are
resolved differently.

**Information request, no binary change.** Answer it in the reply box on the submission detail page.
The "Resubmit to App Review" button stays disabled, which is correct: the reply is the requested
action.

**A binary change is needed.** Upload a new build, attach it to the version, then resubmit. Attaching
the build is not obvious in the current App Store Connect UI:

1. On the version page, hover the existing build row. A remove control appears in a column that is
   otherwise empty.
2. Remove it, then use "Add Build" and pick the new build. Match the row id against the Delivery UUID
   from the upload.
3. Save the version.

**Resubmitting is two steps, and the first one does not submit.** "Update Submission" on the version
page replaces the contents of the pending submission — it does not return the app to review, and the
submission keeps showing an unresolved issue. The submission then has to be sent with **"Resubmit to
App Review"** on the submission detail page, which only becomes enabled once the contents are
updated. Check the submissions list afterwards: the row must read *Waiting for Review* with a new
submission date.

## Release history

A `v*.*.*` tag is created when the release is cut, and `release-artifacts.yml` triggers on it. A
later iOS build carrying a fix is not covered by that tag, so the commit the shipping iOS binary was
built from can end up unreachable from any ref.

Do not repoint a published tag: its release has artifacts with published checksums and an SBOM, and
[RELEASE_ARTIFACT_TRUST.md](RELEASE_ARTIFACT_TRUST.md) makes those the basis for verifying a
download. Create a marker tag instead, named so it does not match `v*.*.*` and therefore publishes
nothing, and record the relationship in the roadmap's shipped history.

```bash
git tag -a ios-<version>-build<n> <commit> -m "..."
git push origin refs/tags/ios-<version>-build<n>
```
